**테스트로 새로 알아낸 것 2가지**

1. `quest_state`는 문자열 `"0"/"1"/"2"`. 공식 문서에 의미 없음. 관측 기반 추정:

   - `"1"`: 누적형 주간 퀘스트 (꾸준한 의뢰에 대한 보답)
   - `"0"`: 나머지
   
   0=미완료, 1=진행중, 2=완료로 라벨링함. 추정이라 코드 주석에 명시.

Next.js vs Express + React, 핵심 차이만.

**구조**
- Express + React: 프로젝트 2개. `server/` (Express, 포트 3000, API만) + `client/` (Vite React, 포트 5173, 화면만). 브라우저가 화면은 5173에서, 데이터는 3000에서 받음. 배포 시엔 React를 빌드해서 Express가 정적 파일로 같이 서빙하거나 nginx가 나눠줌.
- Next.js: 프로젝트 1개. `app/` 안에 화면 파일과 API 파일이 같이 있음. `app/planner/page.tsx`가 화면, `app/api/plan/route.ts`가 API. 실행도 `npm run dev` 하나.

**렌더링**
- React(Vite): 브라우저에서 전부 그림(CSR). 첫 화면 빈 HTML 받고 JS가 채움. 로그인 뒤 쓰는 대시보드류엔 문제 없음.
- Next.js: 서버에서 HTML 만들어 보냄(SSR) 가능. 검색 노출·첫 로딩에 유리. 파티 모집 게시판을 구글에 노출시키고 싶다면 이점. 대신 "이 컴포넌트는 서버용, 이건 클라이언트용" 구분 규칙(`"use client"`)을 익혀야 함.

**API 로직 위치**
- Express: `maple-proto.js` 함수들을 `server/lib/`로 옮기고 `app.get("/api/plan", ...)`로 감싸면 끝. 현재 코드와 거리 가장 짧음.
- Next.js: 같은 함수를 `route.ts`에서 호출. 거리 비슷함. 단, Node 전용 코드(fs 읽기 등)는 서버 컴포넌트/API에서만 써야 하는 제약.

**백그라운드 작업 (매주 수요일 밤 스냅샷 저장, 5분 캐시)**
- Express: 서버 프로세스가 항상 떠 있으니 `node-cron` 한 줄.
- Next.js: `next start`로 Node 서버 띄우면 가능. Vercel 같은 서버리스에 올리면 프로세스가 안 떠 있어서 cron 불가 → 외부 cron 필요. EC2에 올릴 거면 문제 없음.

**배포**
- 둘 다 EC2에서 pm2 + nginx로 동일하게 가능. Next.js는 Vercel 무료 배포가 매우 쉬운 게 추가 장점.

**학습·디버깅**
- Express + React: 개념 단순. 서버 문제 vs 화면 문제가 명확히 나뉨.
- Next.js: 편의 기능 많지만 App Router 규칙(서버/클라 컴포넌트, 캐싱 동작)이 초반 혼란 유발. 디버깅 시 "왜 이게 서버에서 실행됐지" 류 이슈 겪음.

**이 프로젝트 기준 결론**
- 로컬 테스트 → EC2 공개 흐름이면 둘 다 됨.
- 파티 게시판 SEO 원하면 Next.js. 아니면 Express + React가 단순하고 프로토타입 로직과 가장 가까움.
- 이미 React 경험 있고 Next.js 처음이면 Express + React. Next.js 써봤으면 Next.js도 무리 없음.
